# 030 - WhatsApp Integration via Baileys

## Overview

Add WhatsApp as a messaging channel alongside Telegram, using the `@whiskeysockets/baileys` library (reverse-engineered WhatsApp Web protocol). This enables Snew to reach 95%+ of Brazilian e-commerce merchants who use WhatsApp as their primary communication tool.

**Legal basis**: CADE (Brazilian antitrust authority) ruled in March 2026 that Meta cannot ban third-party AI integrations from WhatsApp in Brazil. Brazil and Italy are explicitly excluded from Meta's restriction policy.

**Key architectural constraint**: Unlike Telegram's stateless Bot API, Baileys requires a persistent WebSocket connection. This necessitates a lightweight **Baileys Gateway Service** running on Fly.io that exposes a REST API matching the Telegram Bot API pattern, enabling the Next.js app to use identical integration patterns.

## User Stories

### US-1: WhatsApp Account Linking (QR Code)

**As a** merchant using Snew,
**I want to** link my WhatsApp account by scanning a QR code,
**So that** I can interact with my Snew agents directly from WhatsApp.

**Acceptance Criteria:**

- User clicks "Link WhatsApp" in Settings → Messaging
- A QR code is displayed (generated by Baileys via the gateway)
- User scans QR code with their WhatsApp phone app
- Connection is established and persisted (survives restarts)
- Status updates in real-time (polling or SSE)
- User can unlink at any time

### US-2: Two-Way Chat via WhatsApp

**As a** merchant with a linked WhatsApp,
**I want to** send messages to Snew via WhatsApp and receive AI responses,
**So that** I can manage my store from WhatsApp without opening the dashboard.

**Acceptance Criteria:**

- Messages sent to the linked WhatsApp number are received by Snew
- Messages are queued for async processing (same as Telegram pattern)
- AI agent processes the message with full platform tools access
- Response is sent back to WhatsApp
- Long messages are split at natural boundaries (WhatsApp limit: ~65,536 chars but practical limit ~4096 for readability)
- Typing indicator shown while processing
- Message history persisted in `agent_messages` with `channel: 'whatsapp'` metadata

### US-3: WhatsApp Notifications from Workflows

**As a** merchant,
**I want to** receive workflow notifications on WhatsApp (stock alerts, order notifications, daily summaries),
**So that** I get critical business alerts on the app I use most.

**Acceptance Criteria:**

- New `send_whatsapp` utility step type in workflow editor
- Same template/variable system as `send_telegram`
- Workflow editor UI shows WhatsApp option alongside Telegram
- Execution engine resolves team's WhatsApp link and sends message
- Works in both `execute-visual-steps.ts` and `webhook-executor.ts`

### US-4: Retail Notifications on WhatsApp

**As a** merchant,
**I want to** receive stock alerts, order notifications, sales summaries, and abandoned cart alerts on WhatsApp,
**So that** I stay informed without checking the dashboard.

**Acceptance Criteria:**

- All existing notification functions support WhatsApp as a channel
- Notifications are sent to ALL verified channels (Telegram AND WhatsApp if both linked)
- Files affected: `order-notifications.ts`, `stock-alerts.ts`, `sales-summary.ts`, `abandoned-cart.ts`

### US-5: AI Workflow Builder WhatsApp Support

**As a** merchant using the AI chat to create workflows,
**I want to** specify WhatsApp as a notification channel,
**So that** AI-created workflows can send me WhatsApp alerts.

**Acceptance Criteria:**

- `channel` enum in skill-builder-tools includes `'whatsapp'`
- AI prompts mention WhatsApp as a preferred channel option
- `SNEW_CREATE_WORKFLOW` generates `send_whatsapp` steps when channel is 'whatsapp'

## Architecture

### Baileys Gateway Service (New — Fly.io)

A lightweight Node.js service that manages WhatsApp connections via Baileys:

```
┌─────────────────────┐       ┌──────────────────────┐
│   Next.js App       │       │  Baileys Gateway     │
│   (Vercel)          │       │  (Fly.io)            │
│                     │       │                      │
│  POST /send ───────────────>│  Send WhatsApp msg   │
│                     │       │                      │
│  /api/messaging/    │<──────│  Webhook forward     │
│  whatsapp/webhook   │       │  (incoming messages) │
│                     │       │                      │
│  GET /qr ──────────────────>│  Generate QR code    │
│                     │       │                      │
│  GET /status ──────────────>│  Connection status   │
│                     │       │                      │
└─────────────────────┘       └──────────────────────┘
                                       │
                                       │ WebSocket
                                       │ (persistent)
                                       ▼
                              ┌──────────────────────┐
                              │  WhatsApp Web         │
                              │  (Meta servers)       │
                              └──────────────────────┘
```

**Gateway REST API:**

- `POST /send` — Send a message (body: `{ to, text }`)
- `GET /qr/:teamId` — Get QR code for pairing
- `GET /status/:teamId` — Connection status
- `POST /disconnect/:teamId` — Disconnect session
- `DELETE /session/:teamId` — Delete session data

**Gateway → App Webhook:**

- `POST /api/messaging/whatsapp/webhook` — Incoming messages forwarded here

**Auth**: Shared secret token in `WHATSAPP_GATEWAY_SECRET` env var.

### Session Management

Baileys sessions are stored in a Fly.io volume (`/data/sessions/{teamId}/`). Each team gets an isolated WhatsApp connection. Session data includes:

- Auth keys (encrypted)
- Connection state
- Pre-keys and signal protocol data

### Channel Abstraction for Notifications

Instead of duplicating notification code, create a `sendToAllChannels()` helper:

```typescript
// src/lib/messaging/channel.ts
export async function sendToAllChannels(
  teamId: string,
  text: string,
  parseMode?: string
): Promise<void> {
  const links = await getVerifiedLinks(teamId) // all channels
  await Promise.allSettled(
    links.map((link) => {
      if (link.channel_type === 'telegram')
        return sendTelegramMessage(link.external_chat_id, text, parseMode)
      if (link.channel_type === 'whatsapp') return sendWhatsAppMessage(link.external_chat_id, text)
    })
  )
}
```

## Database Changes

### New Table: `whatsapp_message_queue`

Mirror of `telegram_message_queue`:

```sql
CREATE TABLE whatsapp_message_queue (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  phone_number TEXT NOT NULL,
  message_text TEXT NOT NULL,
  sender_name TEXT,
  link_id UUID REFERENCES messaging_links(id),
  status TEXT NOT NULL DEFAULT 'pending',
  attempts INTEGER NOT NULL DEFAULT 0,
  error TEXT,
  created_at TIMESTAMPTZ DEFAULT now(),
  processed_at TIMESTAMPTZ
);
```

### Modified: `messaging_links`

No schema changes needed — `channel_type` is already a TEXT field that supports any value. New rows will use `channel_type = 'whatsapp'` with `external_chat_id` storing the WhatsApp phone number (JID format: `5511999999999@s.whatsapp.net`).

## Out of Scope

- WhatsApp Business API (Meta official) — this uses Baileys (reverse-engineered)
- WhatsApp group messaging — DMs only
- Media messages (images, videos, documents) — text only for V1
- WhatsApp status/stories
- End-to-end encryption key backup
- Multi-device linking (one device per team)

---

## Risks

1. **Baileys stability** — Reverse-engineered protocol may break when WhatsApp updates. Mitigation: pin Baileys version, monitor for updates.
2. **Account banning** — WhatsApp may ban numbers using unofficial APIs. Mitigation: CADE ruling protects usage in Brazil; use reasonable message rates.
3. **Session persistence** — Baileys sessions can expire. Mitigation: Auto-reconnect logic in gateway, re-auth notification to user.
4. **Gateway availability** — Single point of failure. Mitigation: Fly.io auto-restart, health checks, graceful degradation (Telegram still works).

---

## Success Criteria

1. User can link WhatsApp via QR code scan
2. Two-way chat works (user ↔ AI agent) via WhatsApp
3. All existing workflow `send_telegram` steps have equivalent `send_whatsapp`
4. All retail notifications (order, stock, sales, abandoned cart) are sent to WhatsApp
5. AI workflow builder can create WhatsApp notification workflows
6. Existing Telegram integration is unchanged (no regressions)
7. Both channels can be linked simultaneously (user gets notifications on both)
