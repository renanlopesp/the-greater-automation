# Implementation Plan: Restore Real Data Integration

**Branch**: `032-restore-data-integration` | **Date**: 2026-03-10 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/032-restore-data-integration/spec.md`

## Summary

The layout redesign (spec 031) replaced 6 page routes with new client components that import static mock data from `/data/`. All server-side Supabase queries, auth checks, and data passing were removed. The query infrastructure in `/lib/queries/` and components in `/components/agent-detail/` remain fully intact. This plan restores real data fetching on all 6 page routes while preserving the new visual design.

**Approach**: For each page route, convert the page from a simple client-component render to an async Server Component that authenticates the user, resolves their team, fetches data via existing query functions, and passes results as props to the client component. The client components need minor modifications to accept props instead of importing static data.

## Page Restoration Strategy

### Page 1: `/agents/[id]` (P0 — CRITICAL)

**Current**: 6 lines rendering `<WorkspaceClient agentId={id} />`
**Target**: Restore from `main` branch (422 lines) with adaptations for new layout components

**Strategy**: The original page.tsx from main is the reference implementation. It contains:

- 2-phase parallel Supabase fetching (auth+agent first, then profile+conversation+role+store+messaging+skills+workflows)
- `buildSetupSteps()` function for context-aware setup checklist
- Orchestrator detection with tailored conversation starters
- `AgentSidebarData` async component for Suspense-streamed sidebar
- Full render with ChatPanel, AgentSidebar, SetupChecklist, PresenceIndicator

**Decision**: Restore the original server-side logic from main. The key question is whether to render the OLD UI components (ChatPanel, AgentSidebar, etc.) or adapt the NEW WorkspaceClient to accept real data. Since the original components still exist and are tested, restore them with the original layout. The new WorkspaceClient was a visual prototype that can coexist for reference.

### Page 2: `/dashboard` (P0)

**Current**: 5 lines rendering `<HomeClientNew />`
**Target**: Async server component calling `fetchTeam()`, `fetchAgentsWithSkills()`, `fetchWorkflows()`, `fetchRunsToday()`

**Strategy**: Restore server-side fetching from main's original page. Modify `HomeClientNew` to accept props for team, agents, workflows, and run count. Keep the new visual design but replace static data imports with prop usage.

### Page 3: `/history` (P1)

**Current**: 5 lines rendering `<HistoryClient />`
**Target**: Server component fetching `agent_conversations` for the user

**Strategy**: New server-side fetch (this page didn't exist on main). Query `agent_conversations` filtered by `user_id`, join agent names. Modify `HistoryClient` to accept conversations as props.

### Page 4: `/apps` (P1)

**Current**: 5 lines rendering `<AppsClient />`
**Target**: Server component fetching app connections + Composio catalog

**Strategy**: New server-side fetch. Use `getAppConnections()` from Composio actions + query `app_connections` table. Modify `AppsClient` to accept apps + connection status as props.

### Page 5: `/agents` discover (P2)

**Current**: 5 lines rendering `<DiscoverClient />`
**Target**: Server component fetching agents from database

**Strategy**: New server-side fetch. Use `fetchAgentsWithSkills()` or a simpler agents query. Modify `DiscoverClient` to accept agents as props.

### Page 6: `/chat` (P2)

**Current**: 5 lines rendering `<NewChatClient />`
**Target**: Server component fetching available agents for chat

**Strategy**: Fetch team agents list. Modify `NewChatClient` to accept agents as props for the coworker selector. Wire up message sending to create real conversations.
