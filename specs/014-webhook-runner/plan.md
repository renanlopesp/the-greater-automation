## Summary

Implement the webhook runner — a public endpoint that receives external HTTP requests, validates method and secret, creates a workflow run, and executes all steps sequentially. This replaces the current placeholder `resumeWebhook` import with a fully functional handler. The UI is updated to display real webhook URLs instead of placeholder text.

## Architecture

### Webhook Request Flow

```
External Service → POST /.well-known/workflow/v1/webhook/{token}
                       │
                       ▼
              ┌─────────────────┐
              │ Route Handler   │ (route.ts)
              │ 1. Extract token│
              │ 2. Look up trigger by token (webhook_token field in config JSONB)
              │ 3. Validate method
              │ 4. Validate secret
              │ 5. Check workflow is published
              └────────┬────────┘
                       │
                       ▼
              ┌─────────────────┐
              │ Create Run      │
              │ - workflow_run (trigger_type: 'webhook', trigger_data: request payload)
              │ - workflow_run_steps (one per step, status: 'pending')
              └────────┬────────┘
                       │
                       ▼
              ┌─────────────────┐
              │ Execute Steps   │ (reuse existing step executor pattern)
              │ - Sequential    │
              │ - Context accum │
              │ - Error handling│
              └────────┬────────┘
                       │
                       ▼
              Return configured response_status code
```

### Token Lookup Strategy

The webhook token is stored in `workflow_triggers.config` JSONB as a `webhook_token` field. Lookup is done via:

```
workflow_triggers WHERE config->>'webhook_token' = {token} AND type = 'webhook'
```

This avoids any schema migration — the token is just another field in the existing JSONB config column.

### Token Generation

When a webhook trigger is saved and has no `webhook_token` yet, generate one using `crypto.randomUUID()` (produces a non-guessable v4 UUID). Store it in the trigger config alongside `url`, `method`, `secret`, `response_status`.

### Webhook URL Format

The real URL is: `{NEXT_PUBLIC_APP_URL}/.well-known/workflow/v1/webhook/{webhook_token}`

The UI reads `webhook_token` from the saved trigger config and constructs the full URL.

### Execution Engine Reuse

The step execution logic is identical to `execute-scheduled/route.ts`. To avoid duplication, extract the shared step execution loop into a helper function `executeWorkflowSteps()` in `src/lib/workflow-editor/webhook-executor.ts` that both routes can use. This helper:

1. Takes a Supabase client, run ID, workflow ID, and steps array
2. Executes steps sequentially with context accumulation
3. Records step status, output, errors, duration
4. Returns success/failure

### Human-in-Loop in Webhooks

Same as scheduled runs: human-in-loop steps are skipped with a note, since there is no interactive user session to respond to approvals.

## Data Model

### Modified Entity: WebhookTriggerConfig

Add `webhook_token` field to the existing config interface:

```typescript
interface WebhookTriggerConfig {
  url: string // The displayed webhook URL (computed from token)
  method: 'GET' | 'POST' | 'PUT' | 'PATCH'
  secret?: string // Optional secret for validation
  response_status: number // HTTP status code to return (default: 200)
  webhook_token?: string // NEW: unique token for URL routing
}
```

No database migration needed — `webhook_token` is stored in the existing JSONB `config` column.

}

## Contracts

### Webhook Endpoint

**URL**: `/.well-known/workflow/v1/webhook/{token}`
**Methods**: GET, POST, PUT, PATCH (validated against trigger config)
**Auth**: None (public) or `x-webhook-secret` header

**Success Response**:

- Status: Configured `response_status` (default 200)
- Body: `{ "success": true, "run_id": "<uuid>" }`

**Error Responses**:

- `404` — Token not found, workflow not published, or workflow deleted
- `401` — Secret key required but missing/incorrect
- `405` — HTTP method does not match configured method
- `500` — Internal execution error

## Key Decisions

1. **No schema migration**: Store `webhook_token` in existing JSONB config column. Simpler, no migration needed.
2. **Synchronous execution**: Execute workflow steps within the request lifecycle (same as scheduled runner). For long-running workflows, the response may be delayed but the pattern is consistent.
3. **Reuse execution pattern**: Extract shared step execution from `execute-scheduled` to avoid code duplication.
4. **Replace .js with .ts**: Convert the existing JavaScript route handler to TypeScript for type safety.
5. **UUID tokens**: Use `crypto.randomUUID()` for tokens — sufficient entropy, no extra dependencies.
6. **Token generation on save**: Generate token when trigger is saved (not on workflow creation), so tokens only exist for workflows that actually have webhook triggers.
